## 1. Tool interface (`Tool.ts`)

`Tool.ts` defines the entire contract. A tool is a plain object built via `buildTool()` (Tool.ts:783), which fills defaults from `TOOL_DEFAULTS` (Tool.ts:757): `isEnabled → true`, `isConcurrencySafe → false` (fail-closed: assume NOT parallel-safe), `isReadOnly → false` (assume writes), `isDestructive → false`, `checkPermissions → allow`, `toAutoClassifierInput → ''` (skip classifier), `userFacingName → name`.

Core members of `Tool<Input, Output, P>` (Tool.ts:362–695):

| Member | Role |
|---|---|
| `name`, `aliases?` | identity; lookup via `toolMatchesName` (Tool.ts:348) |
| `inputSchema` (Zod) + `inputJSONSchema?` | schema; Zod→JSON-Schema via `utils/zodToJsonSchema.ts`; MCP tools may pass raw JSON Schema |
| `call(args, context, canUseTool, parentMessage, onProgress?)` | execution; returns `ToolResult<T>` |
| `prompt(options)` | system-prompt text for the tool |
| `description(input, opts)` | one-line per-call description |
| `validateInput?(input, ctx)` | hard validation → `{result:true}` or `{result:false, message, errorCode}` (Tool.ts:95) |
| `checkPermissions(input, ctx)` | tool-specific permission logic; only called after validateInput passes (Tool.ts:500) |
| `isReadOnly`, `isConcurrencySafe`, `isDestructive?` | scheduling + permission hints |
| `requiresUserInteraction?()` | if true, an `ask` result survives even bypassPermissions (permissions.ts:1231, 1e) |
| `isOpenWorld?` | open-world flag (plan-mode heuristics) |
| `shouldDefer?` / `alwaysLoad?` / `searchHint?` | ToolSearch deferral (`defer_loading: true`) |
| `maxResultSizeChars` | per-tool result persist threshold; `Infinity` for Read (never persisted — avoids Read→file→Read loop) (Tool.ts:466) |
| `mapToolResultToToolResultBlockParam(content, toolUseID)` | serializes output to an API `tool_result` block |
| `renderToolUseMessage` / `renderToolResultMessage` / `renderToolUseRejectedMessage` / `renderToolUseErrorMessage` | Ink UI hooks; omitted → fallback components |
| `preparePermissionMatcher?(input)` | pre-compiles matcher for rule content like `git *` (Tool.ts:514) |
| `backfillObservableInput?(input)` | mutate a *copy* of input before hooks/SDK/canUseTool see it; original API input untouched (cache preservation) (Tool.ts:481) |
| `toAutoClassifierInput(input)` | compact form fed to the auto-mode security classifier |
| `interruptBehavior?()` | `'cancel' \| 'block'` when user submits mid-run (default `'block'`) |
| `mcpInfo?`, `isMcp?`, `isLsp?`, `isTransparentWrapper?` (REPL) | auxiliary flags |

`ToolResult<T>` = `{ data: T; newMessages?; contextModifier?; mcpMeta? }` (Tool.ts:321). `contextModifier` is only honored for tools that are NOT concurrency-safe. Progress flows through `ToolProgress<P> = { toolUseID, data }`; hook progress is filtered out of tool progress via `filterToolProgressMessages` (Tool.ts:312).

`ToolUseContext` (Tool.ts:158–300) carries: `options` (tools, mcpClients, isNonInteractiveSession…), `abortController`, `readFileState: FileStateCache` (the read-before-edit ledger), `getAppState/setAppState`, `messages`, `agentId`/`agentType` for subagents, `localDenialTracking`, `contentReplacementState`, `requestPrompt?` (interactive prompts), plus UI callbacks.

Result-size system constants (`constants/toolLimits.ts`):
- `DEFAULT_MAX_RESULT_SIZE_CHARS = 50_000` — system-wide cap even if a tool declares higher; over-size results are persisted to disk and the model gets a preview + file path.
- `MAX_TOOL_RESULT_TOKENS = 100_000`, `BYTES_PER_TOKEN = 4` → `MAX_TOOL_RESULT_BYTES = 400KB`.
- `MAX_TOOL_RESULTS_PER_MESSAGE_CHARS = 200_000` — aggregate per-turn budget for one batch of parallel tool_results; largest blocks persisted until under budget. Overridable via GrowthBook `tengu_hawthorn_window`.
- `TOOL_SUMMARY_MAX_LENGTH = 50`.

## 3. Bash deep-dive

- **Params**: `command`, optional `timeout` (ms, described with `getMaxTimeoutMs()`, BashTool.tsx:229), `run_in_background` (BashTool.tsx:241: "Set to true to run this command in the background. Use Read to read the output later…" — output retrieval via TaskOutput). Background flag stripped from schema when background tasks disabled (BashTool.tsx:253–255).
- **Timeouts**: `utils/timeouts.ts` — `DEFAULT_TIMEOUT_MS = 120_000` (2 min), `MAX_TIMEOUT_MS = 600_000` (10 min); env overrides `BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`; max is floored at default.
- **Output cap**: `BASH_MAX_OUTPUT_DEFAULT = 30_000` chars, upper bound `BASH_MAX_OUTPUT_UPPER_LIMIT = 150_000`, env `BASH_MAX_OUTPUT_LENGTH` (utils/shell/outputLimits.ts).
- **Background**: `run_in_background: true` honored unless disabled (BashTool.tsx:986–989). Additionally an assistant-mode "blocking budget" (`ASSISTANT_BLOCKING_BUDGET_MS = 15_000`, BashTool.tsx:57): commands exceeding it are auto-moved to background with a notification (BashTool.tsx:610). Blocking sleep commands are refused with advice to background them (BashTool.tsx:525–530).
- **Persistence / snapshots**: `utils/bash/ShellSnapshot.ts` — creates a shell environment snapshot by sourcing the user's shell config into a snapshot file that subsequent shells source (ShellSnapshot.ts:389–411), restoring functions/aliases/env; includes ripgrep and find/grep shell-integration function injection (ShellSnapshot.ts:65,153). Snapshot creation failure is non-fatal (CLI still starts). Underlying command parsing uses a tree-sitter based parser (`utils/bash/bashParser.ts`, `ast.ts`, `heredoc.ts`, `commands.ts` incl. `extractOutputRedirections`).
- **Permissions**: `tools/BashTool/bashPermissions.ts` evaluates per-command rules against the parsed command list; `bashSecurity.ts` + `pathValidation.ts` + `sedValidation.ts` + `readOnlyValidation.ts` + `modeValidation.ts` implement security/anti-injection checks; `shouldUseSandbox.ts` decides sandboxing (sandbox auto-allow interacts with ask rules, permissions.ts:1186–1206).
- **Windows**: a parallel PowerShellTool exists (its own permissions/security/pathValidation mirrors), selected via `isPowerShellToolEnabled()`; `utils/shell/powershellDetection.ts` + `resolveDefaultShell.ts`.

## 4. Edit & Write mechanics (`tools/FileEditTool/`)

- **Exact-string matching with fallbacks** (`utils.ts`): `findActualString` (utils.ts:73) tries exact `includes`, then retries after normalizing curly→straight quotes (model can't emit curly quotes; utils.ts:18–37). `preserveQuoteStyle` re-applies the file's curly-quote style to `new_string` (utils.ts:104). `normalizeFileEditInput` (utils.ts:581) additionally tries a de-sanitization table (`<fnr>`→`<function_results>` etc., utils.ts:531) and strips trailing whitespace from `new_string` (skipped for `.md/.mdx` to preserve hard line breaks).
- **Application** (`applyEditToFile`, utils.ts:206): `replaceAll ? content.replaceAll : content.replace` with a function replacement (avoids `$` pattern semantics). When `new_string === ''` and `old_string` doesn't end with `\n` but `old_string + '\n'` exists, the trailing newline is stripped too.
- **Multi-edit safety** (`getPatchForEdits`, utils.ts:262): edits applied sequentially; throws `'String not found in file. Failed to apply edit.'` if an edit changes nothing; throws if `old_string` is a substring of any previously-applied `new_string` (prevents self-matching); throws `'Original and edited file match exactly'` if nothing changed overall.
- **Diff generation**: `structuredPatch`/`getPatchFromContents` from the `diff` lib with `DIFF_TIMEOUT_MS`; display converts leading tabs to spaces; patch is display-only (utils.ts:339–348). Rejected-edit UI + snippet functions (`getSnippetForPatch`, `CONTEXT_LINES = 4`, utils.ts:408) live alongside.
- **Must-Read-first enforcement**: enforced through `readFileState: FileStateCache` in ToolUseContext (Tool.ts:181) — the tool compares file mtime against the cached read time (`getFileModificationTime`, utils/file.ts, floors mtimeMs). Cache is an LRU: `READ_FILE_STATE_CACHE_SIZE = 100` (utils/fileStateCache.ts:18). Exact error-string wording in FileEditTool.ts was not read in full (**unverified** wording; mechanism verified via ToolUseContext/fileStateCache and FileReadTool's readFileState bookkeeping at FileReadTool.ts:553).

## 5. Permission engine

### 5.1 Types & data (`types/permissions.ts`)

- Modes: external `['acceptEdits','bypassPermissions','default','dontAsk','plan']`; internal adds `'auto'` (TRANSCRIPT_CLASSIFIER feature) and `'bubble'` (types/permissions.ts:16–29).
- Behaviors: `'allow' | 'deny' | 'ask'`. Rules: `{ source, ruleBehavior, ruleValue: {toolName, ruleContent?} }`. Sources: `userSettings | projectSettings | localSettings | flagSettings | policySettings | cliArg | command | session`.
- Decisions: `PermissionAllowDecision` (may carry `updatedInput`, `acceptFeedback`, `contentBlocks`), `PermissionAskDecision` (`suggestions: PermissionUpdate[]`, `blockedPath`, `pendingClassifierCheck`), `PermissionDenyDecision`, plus `'passthrough'` (converted to ask at the end). Decision reasons: `rule | mode | subcommandResults | permissionPromptTool | hook | asyncAgent | sandboxOverride | classifier | workingDir | safetyCheck | other`.
- Context (`ToolPermissionContext`, Tool.ts:123): `mode`, `additionalWorkingDirectories` Map, `alwaysAllowRules/alwaysDenyRules/alwaysAskRules: RulesBySource`, `isBypassPermissionsModeAvailable`, `shouldAvoidPermissionPrompts` (headless), `strippedDangerousRules`, `prePlanMode`.

### 5.2 Rule strings (`permissionRuleParser.ts`)

Format `ToolName` or `ToolName(content)`; `Bash()` and `Bash(*)` mean tool-wide. Content may escape parens/backslash (`escapeRuleContent`: backslashes first, then parens). Legacy aliases normalize at parse: `Task→Agent`, `KillShell→TaskStop`, `BashOutputTool/AgentOutputTool→TaskOutput` (permissionRuleParser.ts:21–29). MCP rules: `mcp__server` or `mcp__server__*` match all tools of a server; `mcp__server__tool` is specific (permissions.ts:258–268). Bash content matching uses prefix patterns like `npm:*` (matching implemented in `shellRuleMatching.ts` + BashTool's `preparePermissionMatcher`).

### 5.3 Evaluation order — `hasPermissionsToUseTool` (permissions.ts:473 → Inner at 1158)

1. **1a** whole-tool deny rule → **deny** (1169–1181).
2. **1b** whole-tool ask rule → **ask**, except when Bash + sandboxing enabled + `autoAllowBashIfSandboxed` + command would be sandboxed (1186–1206).
3. **1c** `tool.checkPermissions(parsedInput)` — tool-specific logic (Bash subcommand rules etc.) (1208–1223).
4. **1d** tool returned deny → **deny** (1225).
5. **1e** `tool.requiresUserInteraction()` + ask → **ask**, survives bypass (1230).
6. **1f** content-specific ask rule surfaced by checkPermissions (e.g. `Bash(npm publish:*)`) → **ask** even in bypassPermissions (1238–1250).
7. **1g** `safetyCheck` asks (`.git/`, `.claude/`, `.vscode/`, shell configs) → **ask**, bypass-immune (1252–1260).
8. **2a** mode bypass: `mode === 'bypassPermissions'` or (`plan` + `isBypassPermissionsModeAvailable`) → **allow** (1262–1281).
9. **2b** whole-tool allow rule → **allow** (1283–1297).
10. **3** leftover `passthrough` → **ask** (1299–1310).

Outer wrapper then post-processes (permissions.ts:480–956):
- **dontAsk** mode: any `ask` → **deny** with `DONT_ASK_REJECT_MESSAGE` (503–517).
- **auto** mode (ant classifier): runs fast-paths before the LLM classifier — non-approvable safetyCheck immune; `requiresUserInteraction` tools pass through; PowerShell blocked unless `POWERSHELL_AUTO_MODE`; re-runs `checkPermissions` with mode temporarily set to `acceptEdits` to skip the classifier for edits (600–656); safe-tool allowlist (`classifierDecisionModule.isAutoModeAllowlistedTool`); then `classifyYoloAction()` over the transcript. Classifier deny → deny; 3 consecutive or 20 total denials → fall back to prompting (`DENIAL_LIMITS`, denialTracking.ts:12–15); headless + limit → AbortError. Classifier unavailable → fail-closed via GrowthBook `tengu_iron_gate_closed` (default true, 30-min refresh) or fail-open fallback (843–876).
- **shouldAvoidPermissionPrompts** (headless/background agents): run PermissionRequest hooks; if none decide → **auto-deny** with `AUTO_REJECT_MESSAGE` (929–952).
- `checkRuleBasedPermissions` (1071) exposes steps 1a–1g only — this is the subset bypassPermissions still respects; used by speculation/classifier paths.

So the effective precedence is **deny > ask > allow > mode**, with hook- and safety-asks overriding even bypass mode.

### 5.4 Modes & cycling

- `default`: prompt for anything not allow-ruled. `acceptEdits`: auto-accept file edits in the working directory (implemented inside FileEdit/FileWrite `checkPermissions`). `plan`: read-only planning; exiting plan + `isBypassPermissionsModeAvailable` retains bypass. `bypassPermissions`: skip prompts (except 1e/1f/1g). `dontAsk`: ask→deny. `auto` (ant): classifier decides.
- Shift+Tab cycle (`getNextPermissionMode.ts`): default→acceptEdits→plan→(bypassPermissions|auto)→default; ants skip acceptEdits/plan. `cyclePermissionMode` also calls `transitionPermissionMode` which strips dangerous rules on entering auto (`strippedDangerousRules`).
- Bypass has a killswitch (`bypassPermissionsKillswitch.ts`) and settings can set `disableBypassPermissionsMode: 'disable'` (settings schema, utils/settings/types.ts).

### 5.5 Where rules live (settings.json)

`utils/settings/types.ts` SettingsSchema: `permissions: { allow: string[], deny: string[], ask: string[], defaultMode, disableBypassPermissionsMode: 'disable', additionalDirectories: string[], (disableAutoMode) }` — file hierarchy user (`~/.claude/settings.json`) → project (`.claude/settings.json`) → local (`.claude/settings.local.json`) → flag (`--settings`) → policy (managed). `permissionsLoader.ts` merges; `syncPermissionRulesFromDisk` (permissions.ts:1419) does full replace of disk sources each sync (with managed-only mode clearing everything else); `applyPermissionRulesToPermissionContext` adds rules at startup. `PermissionUpdate` ops: `addRules/replaceRules/removeRules/setMode/addDirectories/removeDirectories` with destination (types/permissions.ts:98–131); `persistPermissionUpdates` writes them back (used by PermissionRequest-hook allows, permissions.ts:425).

### 5.6 Approval prompts

Decisions surface as `PermissionResult`s consumed by `hooks/useCanUseTool.js` (CanUseToolFn) and rendered by `components/permissions/*` (15 files) driven by `hooks/toolPermission/handlers/interactiveHandler.ts` (20.7KB). Ask messages come from `createPermissionRequestMessage` (permissions.ts:137) which explains *why* (rule source, hook name, classifier, subcommand list with redirections stripped). Ask decisions can carry `suggestions` (e.g. "always allow Bash(npm:*)") which the dialog offers as one-click persists via `PermissionUpdate`. Headless/swarm variants: `coordinatorHandler.ts`, `swarmWorkerHandler.ts`; logging in `permissionLogging.ts`. Sandbox auto-allow: Bash ask can be pre-empted when the command will run sandboxed (`autoAllowBashIfSandboxed`).

## 6. Hooks

### 6.1 Events (27) — `entrypoints/sdk/coreTypes.ts` HOOK_EVENTS

`PreToolUse, PostToolUse, PostToolUseFailure, Notification, UserPromptSubmit, SessionStart, SessionEnd, Stop, StopFailure, SubagentStart, SubagentStop, PreCompact, PostCompact, PermissionRequest, PermissionDenied, Setup, TeammateIdle, TaskCreated, TaskCompleted, Elicitation, ElicitationResult, ConfigChange, WorktreeCreate, WorktreeRemove, InstructionsLoaded, CwdChanged, FileChanged`

### 6.2 Config shape

settings.json `hooks: { <Event>: [{ matcher: string, hooks: [{ type: 'command', command, timeout?, ... } | { type: 'prompt', ... }] }] }` — parsed in `utils/hooks/hooksSettings.ts` (`HookMatcher { matcher?, hooks }`, HookSource union at hooksSettings.ts:15); matcher applies to tool name for tool events (e.g. `"Bash|Edit"`); skill/agent frontmatter hooks register as session-scoped hooks (`registerFrontmatterHooks.ts`, `registerSkillHooks.ts`, `sessionHooks.ts`; `once: true` auto-removes; agent Stop→SubagentStop conversion). Hook types executed: command (child process), prompt (`execPromptHook.ts`), HTTP (`execHttpHook.ts`), agent (`execAgentHook.ts`), plus internal callback/function hooks (`HookCallback`, types/hooks.ts:211). Timeout per hook; async protocol: `{"async": true, "asyncTimeout": n}` first response, final result later (`hookJSONOutputSchema`, types/hooks.ts:169; AsyncHookRegistry.ts).

### 6.3 Hook output contract (`types/hooks.ts` syncHookResponseSchema)

Common fields: `continue` (default true), `suppressOutput`, `stopReason`, `decision: 'approve'|'block'`, `reason`, `systemMessage` (warning shown to user), plus `hookSpecificOutput` discriminated by `hookEventName`:
- **PreToolUse**: `permissionDecision` (allow/deny/ask), `permissionDecisionReason`, `updatedInput` (rewrites the tool call), `additionalContext` (injected as context).
- **UserPromptSubmit / SessionStart / Setup / SubagentStart / Notification / PostToolUse / PostToolUseFailure**: `additionalContext`; SessionStart also `initialUserMessage`, `watchPaths`; PostToolUse also `updatedMCPToolOutput`.
- **PermissionRequest**: full `decision {behavior:'allow', updatedInput?, updatedPermissions?} | {behavior:'deny', message?, interrupt?}` (types/hooks.ts:122–133). Allow path persists `updatedPermissions` and applies them to the context (permissions.ts:422–443).
- **PermissionDenied**: `retry: boolean`.
- **Elicitation/ElicitationResult**: `action accept|decline|cancel`, `content`.
- **CwdChanged / FileChanged**: `watchPaths`.
- **WorktreeCreate**: `worktreePath`.

Exit-code-2 and `{decision:"block"}` JSON both produce blocking behavior; `services/tools/toolHooks.ts` turns blocking results into a `hook_blocking_error` attachment fed back to the model (toolHooks.ts:90–140) and merges `additionalContexts` into the next turn. Aggregated results (`AggregatedHookResult`, types/hooks.ts:277) carry `preventContinuation`, `stopReason`, `permissionBehavior`, `updatedInput`, `retry`.

### 6.4 Execution pipeline

`services/tools/toolHooks.ts` (23KB) runs hooks around tool execution (PreToolUse before permission dialog and can veto; PostToolUse/PostToolUseFailure after), `utils/hooks/hooksConfigManager.ts` + `hooksConfigSnapshot.ts` merge static + session + plugin hooks, `executeHooks` aggregates, and `fileChangedWatcher.ts` implements FileChanged via `watchPaths`. Progress appears in UI as `HookProgress {type:'hook_progress'}` (types/hooks.ts:234). Hook inputs get `session_id, transcript_path, cwd, permission_mode, agent_id?, agent_type?` (`BaseHookInputSchema`, coreSchemas.ts).

## Vexa implications

- **Mirror the Tool contract 1:1**: a single `Tool` object with Zod `inputSchema`, `validateInput` (hard errors) → `checkPermissions` (soft permission hint) → `call` returning `{data, newMessages?}`; a `buildTool` with fail-closed defaults (`isConcurrencySafe=false`, `isReadOnly=false`) keeps new tools safe by default.
- **Two-layer output bounding**: per-tool `maxResultSizeChars` (Read = Infinity) + system caps (50K default, 100K tokens, 200K per turn-message) with persist-to-disk-and-preview overflow. Vexa should copy the per-message aggregate cap, not just per-tool.
- **Bash numbers**: 120s default / 600s max timeout (env-overridable), 30K char output cap (cap 150K), 15s blocking budget before auto-backgrounding, `run_in_background` + TaskOutput/TaskStop pair — all verified constants to replicate.
- **Read throws on 256KB file / 25K token output rather than truncating** (deliberate, tested tradeoff) — Vexa should decide explicitly which behavior it wants; the throw path keeps tool results tiny.
- **Edit needs the full fallback chain**: exact match → curly-quote normalization → de-sanitization, substring-of-previous-new_string guard for multi-edit, and readFileState (mtime, LRU=100) as the must-Read-first ledger.
- **Permission pipeline order is precise and worth copying**: deny rule → ask rule → tool.checkPermissions → tool-deny → interactive-tools → content-ask-rule → safetyCheck (these last three bypass-immune) → bypass mode → allow rule → passthrough→ask; then mode transforms (dontAsk ask→deny, auto classifier, headless auto-deny after PermissionRequest hooks).
- **Rules-as-strings** `Tool` / `Tool(content)` with paren escaping, MCP server prefixes, and legacy aliases gave cheap forward-compat; sources are 8 tiers merged from 5 settings files with `defaultMode`, `additionalDirectories`, `disableBypassPermissionsMode`.
- **Hooks**: 27-event set with one JSON output schema; the high-value subset for Vexa v1 is PreToolUse (permissionDecision/updatedInput/additionalContext), PostToolUse(+Failure), PermissionRequest, UserPromptSubmit, SessionStart, Stop/SubagentStop, plus `async:true` protocol and exit-code-2 blocking.
- **DontAsk + auto modes and denial limits (3 consecutive / 20 total) are the guardrails** that make headless operation survivable — replicate before shipping any non-interactive mode.
- **Registry hygiene**: deny-rule filtering happens before the model sees tools; MCP tools dedupe with built-ins winning and cache-friendly sorting; feature-flag tool gating via dead-code-eliminated requires.
